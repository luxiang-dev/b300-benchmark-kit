# 8×B300 测试项目总使用说明

目标环境为 **Ubuntu 22.04 / 24.04，单节点 8 张物理 NVIDIA B300**。推荐采用与官方 DeepSeek 提交一致的 Ubuntu 24.04、x86_64 环境。CPU 架构、驱动、镜像和 GPU 型号必须匹配；GB300 是不同系统。

本项目有两条准备路线：基础功能/硬件测试包，以及独立的 DeepSeek-R1 MLPerf 扩展。两条路线均在有网环境提前准备，现场运行关闭容器网络。

## 1. 先决定测试目的

| 模式 | 内容 | 所需离线资源 |
| --- | --- | --- |
| `inventory` | 硬件、驱动、ECC、NVLink/拓扑清单 | 代码、主机 Python、nvidia-smi |
| `quick` | 60 秒压力、PyTorch NCCL、Qwen 0.6B、SDXL | 完整基础包 |
| `compare` | GPU 环境检查、与 Oracle 8×B300 对应的 nccl-tests | 完整基础包 |
| `full` | 600 秒压力、NCCL、公测对比、两个 Qwen、SDXL、DCGM | 完整基础包、主机 DCGM |
| `burn` | 默认 3600 秒压力及 full 后续项目 | 同 full |
| `deepseek` | 完整 DeepSeek-R1 FP4；MLPerf v6.0 Offline 性能及准确率 | 独立官方源码、约 395 GiB 权重、数据、缓存、准确率 venv 和 MLPerf 镜像 |

`full` 和 `burn` 不会自动执行 DeepSeek。Qwen 是每卡独立副本；DeepSeek 使用 TP8/EP8。两者吞吐不能混合比较。DeepSeek 公测参考为 **70,325.7 Tokens/s（8 卡整机）**，不再乘 8。

## 2. Ubuntu 主机前提

- Bash、Python 3.10+、coreutils、Docker；运行用户能访问 Docker daemon。
- 8 张完整 B300、MIG 关闭、ECC 开启、无其他 GPU 计算任务。
- 支持该机型和镜像的 NVIDIA 数据中心驱动；程序检查 R580+，具体补丁版本按厂商和镜像要求确认。[CUDA 兼容性说明](https://docs.nvidia.com/deploy/cuda-compatibility/minor-version-compatibility.html)。
- NVIDIA Container Toolkit 已配置给 Docker。[官方安装与配置](https://docs.nvidia.com/datacenter/cloud-native/container-toolkit/install-guide.html)。
- HGX/NVSwitch 的 Fabric Manager/NVLSM、功耗和散热按服务器厂商要求配置。
- full/burn 需要 B300 兼容 DCGM 4.4+ 和 hostengine。缺失时报告为 INCOMPLETE。
- 能读取测试时段内核日志；普通用户缺权限时会得到 REVIEW。应使用有相应权限的运维账号运行或由运维收集该时段日志。

主机无需安装 PyTorch、CUDA Toolkit、Transformers 或本项目 GPU Python 依赖；它们放在固定镜像里。CPU 开发测试依赖也不要安装到 GPU 镜像。

在安装好主机组件后先检查：

```bash
uname -m
python3 --version
nvidia-smi
docker info
bash run.sh inventory /data/b300-results/inventory-001
```

## 3. 准备基础包

在与目标 CPU 架构一致的有网 Linux/Docker 主机上（不要求 GPU）：

```bash
git clone https://github.com/luxiang-dev/b300-benchmark-kit.git
cd b300-benchmark-kit
bash prepare_offline.sh
python3 bundle.py verify
```

脚本下载约 23.14 GiB Qwen/SDXL 固定版本权重，构建 NVIDIA PyTorch 镜像、编译固定 nccl-tests、导出镜像并记录文件哈希。全部完成后应有 `models/`、`images/b300-test.tar`、`images/runtime.inspect.json`、`bundle.sha256.json`。

在目标机重新运行校验会读取完整权重和镜像，速度取决于存储。代码或文档更新后旧 seal 失效，应在准备机重新执行 `python3 bundle.py seal`，再复制并 verify。模型 hash 校验不会因重新 seal 而取消。

把完整目录复制到服务器本地 SSD/NVMe。不要在加载权重时使用低速移动盘；不要使用 FAT32。基础准备机建议留至少 150 GB 空闲，实际镜像大小以构建结果为准。

## 4. 运行基础测试

```bash
cd /data/b300-benchmark-kit
python3 bundle.py verify
bash run.sh quick /data/b300-results/quick-001
bash run.sh compare /data/b300-results/nccl-001
bash run.sh full /data/b300-results/full-001
# 需要更长的显存/计算压力时：
BURN_SECONDS=7200 STAGE_TIMEOUT=10800 bash run.sh burn /data/b300-results/burn-001
```

输出目录必须是新的测试目录。失败立即停止，保存已完成的证据；Ctrl+C/TERM 会清理容器。不要在结果目录中混入以前的日志。Docker 只使用已准备的本地镜像，不自动拉取。

默认每卡测试约 65% HBM，压力阶段温度阈值 85°C。`MAX_GPU_TEMP` 应按机型厂商要求设置，`MEMORY_FRACTION` 允许 0.05–0.80。遥测覆盖整个测试，报告会检查温度阈值；DeepSeek 尚未实现由主机遥测立即停止推理的独立温度 watchdog。

主要参数：

| 环境变量 | 默认 | 用途 |
| --- | ---: | --- |
| `BURN_SECONDS` | 3600 | burn 压力阶段秒数 |
| `STAGE_TIMEOUT` | 7200 | 基础单阶段超时，包含模型加载 |
| `NCCL_PUBLIC_TIMEOUT` | 1800 | 公测 NCCL 超时 |
| `DCGM_TIMEOUT` | 10800 | DCGM 超时 |
| `MEMORY_FRACTION` | 0.65 | 每卡 HBM 压力比例 |
| `MAX_GPU_TEMP` | 85 | 温度阈值（°C） |

## 5. 准备并运行 DeepSeek

完整步骤见 [DeepSeek 专项说明](../README_DeepSeek_MLPerf.md)。基础 `prepare_offline.sh` 不准备此扩展。必须提前完成以下资源：

1. 固定 NVIDIA 与 MLCommons 源码，完整 `.git`、`3rdparty/trtllm`、MLCommons 子模块与 LoadGen。
2. 固定 FP4 checkpoint（80 个分片）、原始 tokenizer/config 元数据、官方 4388 条数据集及官方预处理输出。
3. `/work/.dsr1-acc-venv`，固定的 tokenizer Hub snapshot，以及官方 LiveCodeBench 所需缓存。新增准备入口在官方准备容器内执行：

```bash
python3 /kit/prepare_deepseek_accuracy.py \
  --workspace /submission/closed/NVIDIA --warm-evaluator
```

4. 将该容器的系统安装保存为最终镜像，导出 tar；保留完整源码工作目录（含 venv）和 scratch（含 `hf-cache`）。复制这些目录时保留符号链接和 Linux 权限，推荐 ext4/XFS；不要把包含源码/venv/符号链接的目录直接复制到不支持这些特性的 exFAT。要经 exFAT 搬运时先在 Linux 打 tar 包，到目标 ext4/XFS 解包。
5. 在最终镜像、相同 `/work` 和 `/submission` 挂载、`--network none` 下执行 `deepseek_mlperf.py check`。它会加载 tokenizer、PRM 数学检查器、LiveCodeBench，检查数据 shape/dtype/内容、源码版本、8 卡 GPU 与模型 hash。

现场加载独立镜像并运行：

```bash
docker load -i /data/b300-deepseek-mlperf.tar
export MLPERF_REPO=/data/inference_results_v6.0
export MLPERF_SCRATCH_PATH=/data/mlperf-deepseek-storage
export MLPERF_IMAGE=b300-deepseek-mlperf:6.0
bash /data/b300-benchmark-kit/run.sh deepseek /data/b300-results/deepseek-001
```

官方源码和 scratch 路径不要包含空格或冒号。scratch 要按准备时的同一绝对路径挂载，否则 `build/` 链接可能失效。原基础 seal 不涵盖外部 DeepSeek 资源，模型有独立固定哈希校验。

先性能后准确率，各启动新的 endpoint。完整性能负载至少 105312 条 issued samples；按公测 samples/s 粗估约 94 分钟，另加校验、模型加载和准确率。预检失败时先修环境，避免反复执行数小时测试。

## 6. 看结果及排查

用浏览器打开输出目录的 `report.html`，重点检查 `summary.json`、`public-comparison.json` 和各阶段日志。

| 状态 | 含义 |
| --- | --- |
| PASS | 已要求的项目完成，当前检查未发现问题；仅适用于本次负载 |
| FAIL | 运行失败、数据/结果不合法、新增不可纠正 ECC、Xid 或达到温度阈值 |
| INCOMPLETE | 项目缺失/跳过；inventory 模式本身即不运行负载 |
| REVIEW | 证据需人工复核，如内核日志权限不足、遥测缺卡/异常/间断、历史 ECC |

负载模式退出码：0=PASS，1=FAIL，2=INCOMPLETE/REVIEW；阶段失败可能保留原始非零退出码。inventory 正常采集成功时返回 0，但报告仍为 INCOMPLETE。

常见故障处理：

| 提示 | 检查位置/处理 |
| --- | --- |
| Offline bundle incomplete / SHA256 mismatch | 补齐镜像和权重；确认复制及准备版本一致，重新制作 seal |
| GPU model is not B300 / Expected 8 GPUs | 检查型号、MIG、GPU 可见性与其他占用 |
| Docker GPU 初始化错误 | 按官方指南检查驱动与 Container Toolkit；用已载入镜像运行 `docker run --rm --pull never --network none --gpus all IMAGE_ID nvidia-smi` |
| tokenizer / LiveCodeBench 离线加载失败 | 在有网准备容器执行准确率准备入口，携带 scratch 的 hf-cache，再用最终镜像离线 check |
| dataset int32 shapes / does not match raw dataset | 使用官方固定数据重跑 preprocess；不要自行改 shape/dtype/长度 |
| 无内核日志、遥测未覆盖 8 卡 | 检查运维权限、telemetry.stderr、采集窗口与采样间断 |
| 服务启动超时、harness 失败 | 检查 `deepseek-performance/` 或 `deepseek-accuracy/` 的 server.log / harness.log |
| 吞吐低于公测但测试 PASS | 对照 CPU、驱动、TRT-LLM/NCCL、功耗、温度、NVLink 和存储；不要仅据百分比判硬件故障 |

DeepSeek 对比会重新解析并核对性能及准确率原始日志 SHA256、LoadGen 版本、int32 响应、4388 个唯一索引和平均 token 长度。仅本地复现，尚未自动完成 TEST06、提交检查或 MLCommons 认证。

## 7. 验证范围与下一步优化

仓库的 [Ubuntu CI](https://github.com/luxiang-dev/b300-benchmark-kit/actions/workflows/ubuntu.yml) 在 Ubuntu 22.04/Python 3.10、Ubuntu 24.04/Python 3.12 执行 CPU 回归、UTF-8/LF 和 Bash 检查，以及使用明确模拟 GPU/Docker 的 Linux 启动失败处理测试。**它不构建大型 GPU 镜像、不下载模型，也不执行真实 B300 推理。** 当前验证结果见 [Ubuntu 复查记录](UBUNTU_REVIEW.md)。

优先优化方向：

- 在真实 Ubuntu 24.04 + 8×B300 机器完成 `quick → compare → full → deepseek`，保留原始日志和软件/硬件清单。
- 给外部 DeepSeek 源码、venv、数据、缓存、镜像建立统一的携带资源清单与目标机校验。
- 加入独立 DeepSeek smoke 模式及温度 watchdog；smoke 的缩短结果不参与正式公测百分比。
- 对同一次准备任务减少重复读取约 395 GiB 权重；现场完整校验仍保留，不能用文件大小代替 hash。
- 收集官方实际成功日志作为兼容性回归样本；同机多次测量再确定性能告警阈值。
