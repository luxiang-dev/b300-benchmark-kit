# 采购验货：哪些证据还必须补齐

本项目用于发现配置矛盾、容量/计算错误、稳定性问题及健康告警，不能保证一台服务器“万无一失”，也不自动签发正品或整机收货认证。**技术 PASS 与采购验收是两项不同的结论。** 金额较大时，应让对应机型的厂商/授权服务人员参加验收，并留下部件序列号对应的报告。

目前买方尚不清楚品牌型号、具体采购配置或约定验收条件。因此程序会固定保留 NOT_ACCEPTED / BLOCKED 与待补证项目，而不是把现有机器识别出的配置反过来当作卖方承诺。

## 给卖方的材料清单

以下内容可复制给卖方，请对方书面填写并提供可核实的来源：

1. 整机品牌、准确型号、整机部件号/序列号、生产和交付状态（新机/其他状态），以及保修服务主体和官方查询方式。
2. CPU：型号、数量、核心规格；内存：每根 DIMM 容量/类型/速度/部件号/序列号、插槽配置和总安装容量。
3. 存储：每个 SSD/HDD 的型号、容量、部件号/序列号、固件和新旧状态；RAID/HBA 型号及全部成员盘清单，不能只列操作系统看到的虚拟卷。
4. 网络：每张卡及各端口型号、协议、约定速率，随附线缆/模块、驱动/固件和配套交换设备；明确在哪种网络条件下验收吞吐与错误计数。
5. GPU：8 张 B300 的准确 SKU、形态、部件号、实体板标签序列号、显存规格，以及 NVSwitch/NVLink 配置和保修资格。不要只给截图中的“NVIDIA B300”文字。
6. 电源/散热：PSU 数量、型号和额定规格、整机供电要求/冗余方式、机房适用条件及该机型允许的温度/功耗范围。
7. BIOS、BMC、GPU/NVSwitch、NIC、SSD 和其他部件的交付固件版本及厂商支持的软件组合。
8. 对应机型和当前 B300 SKU 的厂商整机/离线现场诊断报告，包含时间、整机/部件 SN、工具与固件版本、所测项目、原始日志、跳过项和未解决问题。
9. 双方确认的验收项目、持续负载时长、内存/磁盘覆盖要求、网络性能口径、可接受的历史寿命/错误情况，以及由谁复核异常和出具最终结论。

请将程序导出的 `observed-inventory.json` 与这份交付清单逐项比对。缺项、少配、不符、无法核验的序列号或跳过诊断，都应保留为待确认，不能由程序自填或忽略。

## 建议执行顺序

1. **保留原始状态。** 验货前保存实物标签、整机/BMC 清单、ECC/行重映射、SMART、SEL 和固件信息。不先清错误计数、清日志或更新固件来制造“零错误”结果。
2. **核对来源与配置。** 根据卖方书面清单和官方保修/授权渠道确认，而不是仅相信卖方截图或本机驱动显示。软件身份一致不能证明采购来源。
3. **运行本项目 identity/authenticity。** 使用新结果目录、空闲维护窗口和同一运维账号。观察每张 GPU 的实际 HBM 覆盖、计算时长、通信、温度、前后错误，以及全部可见磁盘/BMC 的健康证据。
4. **完成机型专用整机验收。** 全核 CPU、主机 RAM 全面诊断、全部成员盘介质/健康、各 NIC/外部链路、PSU/风扇、冷启动及持续稳定性依照该厂商规范执行。程序的 256 MiB RAM / 128 MiB 临时结果文件抽查不覆盖这些项目。
5. **复核原始证据。** 保存每次报告和自包含的 ZIP。对 FAIL、REVIEW、INCOMPLETE、错误计数、历史磨损和任何未知字段，让厂商提供原因、处理措施和复测证据。
6. **人工确认最终验收。** 不将一次技术 PASS、低于/高于某公测比例或一个健康字符串当成整机收货依据。本项目的采购状态不会自动变为 ACCEPTED。

不要自行断电、拔 PSU、写裸盘、更新固件或执行不明来源的诊断二进制。此类机型专项操作需按厂商流程，在维护窗口由具备相应权限的人员完成。

## 程序这次加严了什么

- 新 GPU 结果绑定本轮 run_id、原始硬件快照 SHA、具体 UUID/PCI 地址、CUDA 架构和容量，拒绝陈旧或仅写 PASS 的文件。
- 实际压力时间、矩阵、显存覆盖和 NCCL 口径纳入校验；HBM 低于目标覆盖保留 REVIEW，不把累计读验字节算成容量。
- 地址模式全分配写读之外，每 chunk 增加独立 CPU 算法三点抽查。抽查不是全显存 CPU 校验。
- 检查寿命/易失 ECC、行重映射、NVLink 计数/链路、fabric、恢复动作和内核日志完整性。历史/可纠正错误要求复核，不直接声称是假货。
- DCGM 新格式须证明核心诊断项目覆盖全部 GPU；只有某个 Pass 字符串、缺卡、未知格式或跳过项目不能算完整诊断通过。
- 全部可见 disk 节点只读 SMART、当前 BMC 告警及前后计数参与报告。RAID 隐藏成员、虚拟后端和无法读取的设备仍需外部验收。
- 网页与 CLI 共用作业锁，拒绝旧目录；磁盘满不能阻止停止信号；封存按实际 ZIP 字节计算 SHA，并检测仍在变化的证据。

## 官方依据与适用范围

- [NVIDIA DCGM 诊断范围](https://docs.nvidia.com/datacenter/dcgm/latest/learn/modules/dcgm-diagnostics.html)：在线诊断不能替代 NVIDIA 离线现场诊断，也不能自行确定 RMA 资格。
- [nvidia-smi 文档](https://docs.nvidia.com/deploy/nvidia-smi/index.html)：易失与寿命 ECC 的含义不同，GPU 恢复、重映射、fabric/NVLink 状态需要分别解释，不能只看型号和当前零计数。
- **只有确认为 DGX B300 时**，参考 [DGX B300 Quickstart](https://docs.nvidia.com/dgx/dgxb300-user-guide/quickstart-basics.html) 的 NVSM 健康与整机 pre-flight 测试，以及 [BMC 清单与传感器](https://docs.nvidia.com/dgx/dgxb300-user-guide/bmc.html)。其他 HGX/OEM 服务器须使用自己的厂商流程，不能套用 DGX 的工具或安装/保修要求。
- [smartctl 官方手册](https://github.com/smartmontools/smartmontools/blob/main/src/smartctl.8.in)：SMART 健康、历史寿命、错误日志与实际介质诊断不是同一概念；缺失或隐藏设备不算已验证。

当前源码的 CPU/模拟回归与 Ubuntu CI 证明程序处理这些路径，**尚未在买方的真实 8×B300 上完成验收**。现场结果必须在服务器执行后再评估。
